# اصلاح مشکلات ممیزی

۱۷ اکتبر ۲۰۲۶. این مرحله اصلاح کد و تست رگرسیون است؛ اجرای پنج‌روزه تکرار نشد. [گزارش ممیزی](project-audit.fa.md) توصیف وضعیت پیش از اصلاح است.

| یافته | اصلاح انجام‌شده | شواهد بررسی |
|---|---|---|
| A01، توقف tick با فرمان‌های پیوسته | موعد مستقل monotonic، جلوگیری از انباشت tick عقب‌افتاده و صف فرمان با سقف ۲۵۶ | حتی هنگام تغییر پیوستهٔ سرعت، tick پیش می‌رود و pause مؤثر می‌ماند |
| A02، تفاوت RAM و دیتابیس پس از خطا | تراکنش مشترک برای tick، command+step و reset؛ rollback جهان، sequence، cache و نتیجهٔ inference هنگام شکست | تزریق خطا پس از درج SQL؛ hash زنده و replay یکسان می‌ماند؛ writer متوقف‌شده منابعش را آزاد می‌کند |
| A03، معطلی تصمیم به خاطر دیالوگ | taskهای تصمیم و گفت‌وگو جدا، حداکثر چهار گفت‌وگوی هم‌زمان، جلوگیری از جایگزینی تصمیم تازه با پاسخ قدیمی | با دیالوگ معطل، batch دوم محلی اجرا می‌شود |
| A04، انتخاب حرکت بدون انرژی | پیش‌شرط انرژی در نامزدها و استراحت به عنوان قدم لازم برای تهیهٔ غذا | در fixture کنترل‌شده، اولین خوردن از tick پانزده به پنج رسید؛ سه حرکت ناممکن حذف شدند |
| A05، استفاده از ساختمان خراب | تعریف مشترک ساختمان قابل استفاده؛ حذف خرابه از دسترسی و انتخاب‌های اقتصادی؛ بازسازی با پرداخت دوبارهٔ مصالح و چهار مرحلهٔ کار | انبار خراب دسترسی نمی‌دهد؛ بازسازی بدون مصالح رد و با پرداخت یک‌باره کامل می‌شود |
| A06، دلیل قدیمی تصمیم | thought همراه هر عمل تازه به‌روز یا پاک می‌شود | منبع utility دیگر متن توضیح مدل قبلی را نگه نمی‌دارد |
| A07، حذف تاریخچهٔ کلاینت کند | `/api/journal` با watermark، سقف ۱۵۰۰ رویداد قابل نمایش و بازیابی مستقل از snapshot؛ حذف پاسخ run قدیمی | از ۳۰۰ رویداد، فاصلهٔ ۵۰ رویدادی بازیابی شد؛ تست مرورگر پاسخ دیررس پس از reset را رد می‌کند |
| A08، Hold غیرثابت | نگهداری کپی فهرست در Hold و بازنشانی با run جدید | ورود ۱۷۰۰ رویداد تازه فهرست Hold را عوض نمی‌کند؛ reset به Live برمی‌گردد |

در گلوگاه مشاهده نیز مسیر `visible_resources` اضافه شد تا محاسبهٔ خاطره و وضعیت سکونتگاه، tileهایی را که استفاده نمی‌کند نسازد. تست، برابری منابع با دید کامل و عدم فراخوانی ساخت tile را بررسی می‌کند. کپی‌های لازم برای استقلال مشاهدهٔ عامل‌ها حفظ شده‌اند؛ ادعای درصد مشخص افزایش سرعت مطرح نیست.

تراکنش موتور برای rollback یک کپی از جهان پیش از mutation نگه می‌دارد؛ این انتخاب هزینهٔ حافظه/کپی دارد. در مسیر خطای persistence، سرویس روی آخرین حالت commitشده متوقف می‌شود و خطا را ثبت می‌کند؛ retry خودکار روی حالت مشکوک انجام نمی‌شود. موجودی انباری که با خرابی، ظرفیتش کم شده حذف نمی‌شود؛ برداشت مجاز و واریز تا آزادشدن ظرفیت رد می‌شود.

بازیابی journal فقط آخرین ۱۵۰۰ رویداد قابل نمایش را نگه می‌دارد، مطابق سقف رابط. آرشیو کامل همچنان از `/api/events` خوانده می‌شود. watermark شامل رویدادهای داخلی نیز هست؛ نبودِ message به اشتباه شکاف تاریخچه تلقی نمی‌شود. بازیابی قدیمی هنگام تغییر run لغو می‌شود و پاسخ قدیمی در store ادغام نمی‌شود.

## نتیجهٔ بررسی نهایی

- `make check`: هر ۸۱ تست بک‌اند، Ruff، قالب، ESLint، TypeScript و build پاس شدند.
- Playwright با cognition خاموش: هر چهار تست مرورگر پاس شدند؛ دو تست جدید بازیابی journal و Hold را پوشش می‌دهند.
- اسکریپت تشخیصی پس از اصلاح: پیشروی tick در جریان فرمان‌ها، hash یکسان پس از خطا، اجرای batch تازه هنگام انتظار گفت‌وگو، رد دسترسی انبار خراب، پاک‌شدن توضیح و بازیابی کامل فاصلهٔ ۳۰۰ رویدادی تأیید شدند.
- هشدار قبلی deprecation در Starlette/AnyIO و هشدار bundle بیش از ۵۰۰ کیلوبایت باقی‌اند؛ خطای تست یا build نیستند.

پس از تست مرورگر، بهینه‌سازی منابع بدون ساخت tile در مجموعهٔ کامل بک‌اند و تست اختصاصی برابری ادراک بررسی شد. این مرحله benchmark چندروزه یا مقایسهٔ آماری عملکرد ندارد.
